# SkyEx Bot

Telegram-бот для внутреннего учета: кошельки клиентов, обменные заявки, наличные заявки по городам, Google Sheets, AML-проверки, ордера по курсу, рассылки и служебные отчеты.

## Основные Возможности

- Учет клиентских кошельков по валютам: баланс, пополнение, списание, откат операции, выписки.
- Короткие обменные заявки `/пд ... ор ...` с карточками клиента и чата заявок.
- Наличные заявки `/деп*`, `/выд*` и FX-заявки `/прв*`, `/п*вр` по городам.
- Синхронизация заявок с Google Sheets: занесение сделки, удаление строк, чтение внутренних курсов.
- Расписание заявок по городам через `/время`.
- AML-проверка USDT/TRON адресов через GetBlock.
- Ордеры по курсу и live-обновление стакана Rapira/Grinex.
- Учет сделок BestChange, месячных закрытий и выплат партнеру/CoinDrop.
- Контроль отправленных USDT-платежей, счетчик акта и валютный конвертер XE.
- Рассылка клиентам через `/всем`.
- Клиентская база, группы, менеджеры, офисные карточки и отчеты по балансам.
- Архив новых Telegram-сообщений, импорт истории Desktop и ZIP/HTML-выгрузка.

## Переменные Окружения

Обязательные:

- `BOT_TOKEN` — токен Telegram-бота.
- `DATABASE_URL` — строка подключения PostgreSQL.

Доступы:

- `ADMIN_CHAT_ID` — id технического админского чата. Заявки `/заявка` из него не
  меняют кошелёк. Кассовые `/деп*` и `/выд*` меняют только физическую кассу
  выбранного города; баланс самого админ-чата исключён из клиентских итогов.
- `ADMIN_IDS` — user_id админов через запятую, например `123,456`.

Заявки и города:

- `REQUEST_CHAT_ID` — общий чат заявок, legacy/fallback.
- `CASH_CHAT_ID` — карта городов в чаты заявок, например `екб:-1001,члб:-1002`.
- `DEFAULT_CITY` — город по умолчанию, например `екб`.
- `CITY_SCHEDULE_CHATS` — карта городов в чаты расписания.
- `CITY_CASH_CHAT_IDS` — карта городов в операционные чаты физических касс,
  например `екб:-1001,члб:-1002,тюм:-1003`. Один chat ID нельзя привязать к двум
  городам. Это не чаты заявок из `CASH_CHAT_ID`. На старте существующие активные
  `clients` с этими `chat_id` синхронизируются с `cash_chat_registry`; счета и
  история не переносятся, но исключаются из обычных клиентских обязательств. Если
  клиент настроенного чата не найден, запуск останавливается без создания пустого
  дубликата.
- `MOSCOW_POETS_CHAT_ID`, `MOSCOW_BS_CHAT_ID` — будущие гибридные чаты Поэтов и
  BS. После добавления бота их `RUB`-счёт считается московской кассой, а остальные
  валюты того же кошелька остаются клиентскими. Эти чаты работают в тихом режиме:
  `/start` регистрирует кошелёк, валютные команды проводят операции без ответа,
  остальные команды и кнопки игнорируются; общая рассылка их также исключает.

Архив сообщений (по умолчанию выключен):

- `MESSAGE_ARCHIVE_ENABLED=true` — включить live-архив входящих и исходящих сообщений.
- `MESSAGE_ARCHIVE_MEDIA_DIR` — постоянное хранилище фото и голосовых сообщений.
- `MESSAGE_ARCHIVE_TEMP_DIR` — временный каталог ZIP/HTML-экспортов.
- `MESSAGE_ARCHIVE_DOWNLOAD_WORKERS` — число загрузчиков медиа, по умолчанию `2`.
- `MESSAGE_ARCHIVE_DOWNLOAD_QUEUE_SIZE` — размер очереди медиа, по умолчанию `500`.
- `MESSAGE_ARCHIVE_EXPORT_WORKERS` — число параллельных экспортов, по умолчанию `1`.
- `MESSAGE_ARCHIVE_EXPORT_PART_BYTES` — максимальный размер части ZIP, по умолчанию
  `47185920` байт.

Команда `/сообщение <название чата>` доступна менеджерам только в `ADMIN_CHAT_ID`.
Исторический импорт запускается отдельно:

```bash
python scripts/import_telegram_history.py --input /path/to/export --mapping mapping.json --dry-run
python scripts/import_telegram_history.py --input /path/to/export --mapping mapping.json --apply
```

Подробности: [`docs/message_history_feature.md`](docs/message_history_feature.md).
  Scoped-привязка может ждать первого `/start` и активируется сразу после него,
  поэтому предварительно создавать клиента или перезапускать бот не требуется.
  Внутри этих двух чатов проверка роли менеджера заменяется доверием к chat ID.
  `/отпр <сумма>` и `/отпр1 <сумма>` списывают указанную сумму USDT, а `/баотпр`
  списывает весь положительный USDT-остаток. Команды меняют только кошелёк чата и
  не создают сделку или дополнительную бухгалтерскую проводку.
  Пока переменные не заданы, продолжает действовать временный ручной RUB-ledger.
- `SCHEDULE_CHAT_IDS` — чаты ежедневных отчетов по балансам.

Ордера и стаканы:

- `RATE_ORDERS_CHAT_ID` — чат ордеров по курсу.
- `BEST_CHANGE_CHAT_ID` — отдельный чат учета BestChange. Команды этого контура
  перечислены в разделе [BestChange](#bestchange).

Google Sheets:

- `GOOGLE_SHEET_URL` или `GOOGLE_SHEET_ID` — основная таблица.
- `SPREADSHEET_URL` или `SPREADSHEET_ID` — альтернативные имена для основной таблицы.
- `GOOGLE_CREDENTIALS_JSON` или `GOOGLE_SERVICE_ACCOUNT_JSON` — service account JSON inline.
- `GOOGLE_CREDENTIALS_FILE`, `GOOGLE_SERVICE_ACCOUNT_FILE` или `GOOGLE_APPLICATION_CREDENTIALS` — путь к service account JSON.

### Переход московских касс на Telegram-кошельки

До добавления бота в чаты `RUB Мск Поэты` и `RUB Мск BS` продолжают читаться из
временного ручного ledger главной. После настройки соответствующего chat ID
источником становится `client_accounts` Telegram-чата: только `RUB` входит в
кассовый итог, а `EUR`, `USD`, `USDT` и другие валюты входят в клиентские балансы.
Старый RUB-остаток автоматически исключается из итогов при активации нового
источника, поэтому двойного учета нет.

Переходные API до cutover: `GET /api/v1/dashboard/manual-cash`,
`POST /api/v1/dashboard/manual-cash/moves` и
`POST /api/v1/dashboard/manual-cash/moves/{move_id}/reverse`. Для команд записи
обязателен уникальный `idempotencyKey`. После переноса opening в Telegram-кошельки
эти маршруты и ручная панель должны быть удалены; старые движения остаются только
как audit history.

### Импорт accounting snapshot

Импорт принимает нормализованный JSON manifest. Пример со всеми основными типами
записей находится в [`accounting_import_manifest.example.json`](accounting_import_manifest.example.json).
Боевые значения и выгрузки с финансовыми данными в репозиторий добавлять нельзя.

Сначала выполните локальную проверку. Dry-run не требует подключения к БД и не
открывает транзакцию:

```bash
.venv/bin/python scripts/import_accounting_snapshot.py /path/to/manifest.json
```

Сверьте `manifestChecksum`, `recordCount` и все `controlTotals` с утверждённой
выгрузкой. Для каждой валютной позиции в `positionStrategy` должна быть выбрана
ровно одна стратегия: `opening` или `history`. Значения `sourceName` и `records[].key`
после первого применения изменять нельзя.

Применение требует БД с миграцией `0016_import_shadow`, явного `--apply` и checksum
из проверенного dry-run:

```bash
DATABASE_URL=postgresql://... .venv/bin/python scripts/import_accounting_snapshot.py \
  /path/to/manifest.json \
  --expect-checksum <manifestChecksum> \
  --apply
```

Повторный запуск с тем же manifest безопасен: уже записанные source records будут
пропущены, а импорт после сбоя продолжится с сохранённого checkpoint.

Сотруднические RUB-кошельки (`Баланс ВВ`, `Баланс Никита`, `Баланс Влад` и
остальные строки утвержденного блока сотрудников) импортируются только через
`client_accounts`. Попытка поместить их в `internal_balance` отклоняется до начала
записи, чтобы не допустить двойного учета.

### Первичная бухгалтерская приёмка главной

Первый production-запус главной выполняется в режиме бухгалтерской приёмки:

```dotenv
MAIN_DASHBOARD_SOURCE_MODE=db_primary
DASHBOARD_SHADOW_ABSOLUTE_TOLERANCE=0.01
DASHBOARD_SHADOW_RELATIVE_TOLERANCE=0.000001
```

В `db_primary` карточки главной целиком читаются из PostgreSQL. Google Sheets используется
только для shadow-сверки; её отказ не блокирует главную. Бухгалтер видит на
экране источник снимка, предупреждения и раскрываемый отчёт с каждым
расхождением: значение Sheets, значение PostgreSQL, дельта и классификация.

Перед запуском:

1. Создать свежий backup production PostgreSQL. Старый dump на production не
   восстанавливать.
2. Применить Alembic до текущего head и проверить, что миграции не
   остановились на защитном accounting-invariant.
3. Снять синхронные контрольные итоги PostgreSQL и Sheets на один момент.
   Отчёт по свежей таблице нельзя сравнивать со старым dump.
4. Проверить `GET /api/v1/dashboard`, затем раскрыть отчёт на главной.
   Детали также доступны по `GET /api/v1/dashboard/shadow-reports/{report_id}`.
5. Все необъяснённые `real_accounting_error` проверить до перехода на
   `db_only`. Исправления делать только append-only проводками.

Для frontend должны быть заданы `CRM_USE_API=true` и `CRM_API_BASE_URL`.
`db_shadow` не подходит для приёмки DB-цифр: в этом режиме пользователю
показывается цельный Sheets-snapshot.

GetBlock AML:

- `GETBLOCK_IDENTITY`
- `GETBLOCK_PASSWORD`
- `GETBLOCK_LANG` — по умолчанию `en`.
- `GETBLOCK_USER_ID`
- `GETBLOCK_CURRENCY_CODE` — по умолчанию `TRX`.
- `GETBLOCK_TOKEN_ID` — по умолчанию `9`.
- `GETBLOCK_AML_PROVIDER` — по умолчанию `2`.
- `GETBLOCK_DIRECTION` — по умолчанию `2`.
- `GETBLOCK_SOURCE` — по умолчанию `1`.
- `GETBLOCK_TYPE` — по умолчанию `0`.
- `GETBLOCK_REPORTS_DIR` — по умолчанию `reports`.

## Доступы

- **Все** — команда не требует роли.
- **Менеджер** — пользователь из таблицы менеджеров, `ADMIN_IDS` либо участник
  разрешенного админского чата.
- **Админ-чат** — команда работает только в чате `ADMIN_CHAT_ID` или другом
  явно настроенном административном чате.
- **Спецчат** — команда дополнительно ограничена назначенным ей чатом, например
  `BEST_CHANGE_CHAT_ID`, `RATE_ORDERS_CHAT_ID` или чатом заявок.

Если у раздела не указано иное, операционные команды доступны менеджерам.
Ниже перечислены команды, которые фактически регистрируются обработчиками из
`handlers/`; устаревшие названия `/город` и `/проходка` не используются.

## Команды Telegram

### Базовые

- Доступ: **все**.
- `/start` — регистрация/обновление клиента и приветствие.
- `/помоги` — краткая справка.
- `/help` — список команд.
- `/info` — возможности SKYEX, направления работы и контакты команды.
- `/кнопки` — показать основную клавиатуру.
- `/скрыть` — скрыть клавиатуру.
- `/whoami` — показать user_id/chat_id.

### Кошельки Клиентов

- Доступ: **все**; операции выполняются в кошельке текущего чата.
- `/кошелек` — показать все счета клиента.
- `/дай` — показать только ненулевые счета.
- `/дай <валюта>` — показать счет по конкретной валюте.
- `/добавь <валюта> [точность]` — добавить валюту клиенту.
- `/удали <валюта>` — удалить валюту с подтверждением.
- `/<валюта> <сумма|expr> [комментарий]` — изменить баланс.

Примеры:

```text
/кошелек
/дай
/дай USDT
/добавь USD 2
/добавь юсдт 0
/удали USD
/USD 250
/RUB -100
/USDT (2+3*4)
/дол 1000 оплата
```

`/перевод <сумма> [валюта] <точное название чата>` переводит средства между
клиентскими кошельками. По умолчанию валюта — RUB; можно явно указать USDT,
USD, USDW, EUR, EUR500 или THB. Например: `/перевод 1000 Иван Иванов` и
`/перевод 100 USDT Иван Иванов`. Команду может отправить только менеджер.
При совпадающих названиях бот предложит выбрать чат по названию и chat_id.
Если средств не хватает, бот покажет предупреждение с кнопками «Подтвердить
перевод» и «Отклонить»; нажать их может только менеджер. Подтверждённый
перевод может увести баланс отправителя в минус. Операция создаёт сделку
«Перевод» в CRM и две связанные проводки — списание и зачисление; общая
сумма клиентских балансов не меняется. Оба чата получают чек с суммой,
статусом, номером операции, отправителем, получателем и временем, а также
сообщение о своём новом балансе. Кассовые счета не участвуют.

На вкладке «Сделки» CRM перевод создаётся тем же типом сделки: выбираются
отправитель, получатель, валюта и сумма. При нехватке средств интерфейс
отдельно запрашивает подтверждение отрицательного баланса.

В кассовых чатах можно указывать клиента для дублирования операции:

```text
/USD 1000 Иван Иванов
/RUB -50000 Иван Иванов ! комментарий
```

В чате заявок динамические команды изменения кошелька (`/USD`, `/RUB` и т. п.)
отключены.

### Публичный USDT Кошелек

- Доступ к `/кош`: **все**. Доступ к `/setwallet`: **админ-чат**.
- `/кош` — показать USDT TRC-20 кошелек.
- `/setwallet <адрес>` — задать USDT TRC-20 кошелек в админском чате.

### Короткие Обменные Заявки

Доступ: **менеджер**.

Формат:

```text
/<что получаем> <сумма|expr> <что отдаем> <сумма|expr> [комментарий]
```

Получаем:

- `/пд` — USD
- `/пе` — EUR
- `/пт` — USDT
- `/пр` — RUB
- `/пб` — USDW
- `/пбат` — THB
- `/пп` — EUR500
- `/прмск` — RUB Moscow
- `/прспб` — RUB SPB
- `/прпер` — RUB Perm

Отдаем:

- `од` — USD
- `ое` — EUR
- `от` — USDT
- `ор` — RUB
- `об` — USDW
- `обат` — THB
- `оп` — EUR500
- `ормск` — RUB Moscow
- `орспб` — RUB SPB
- `орпер` — RUB Perm

Примеры:

```text
/пд 1000 ор 91000 Клиент Петров
/пр 100000 от 100000/94 срочно
/пт 700 од 700*1.08
/пб 5000 от 5000/1.02
/пр 1000 обат 1000/2.7
/пбат 1000 ор 1000*2.7
```

Поведение:

- В чате клиента создается карточка с клиентским номером заявки.
- В чате заявок создается карточка с номером заявки и номером для таблицы.
- В чате заявок доступна кнопка `Занести в таблицу`.
- Для обмена «получаем USD/EUR/USDW/THB → отдаём USDT» кнопка создаёт две строки
  с одним номером заявки: «Покупка» полученной валюты и «Продажа» USDT.
- В чате клиента доступна отмена.
- При редактировании нужно ответить новой командой на карточку бота.
- При отмене бот возвращает балансы; если заявка была занесена в таблицу, предложит удалить строки из Google Sheets.

### Наличные Заявки

Доступ: **менеджер**.

Формат:

```text
/<команда> [город] <сумма|expr> [контакт 1] [контакт 2] [! комментарий]
```

Депозит:

- `/депр` — RUB
- `/депт` — USDT
- `/депд` — USD
- `/депе` — EUR
- `/депб` — USDW

Выдача:

- `/выдр` — RUB
- `/выдт` — USDT
- `/выдд` — USD
- `/выде` — EUR
- `/выдб` — USDW

Примеры:

```text
/депр 1000
/выдр 1000
/депт екб 100
/выдд члб 500 Иван Петров
/депр члб (50000+10000) Кассир Клиент ! срочно
```

В обычном клиентском чате фактическое проведение меняет кассу и баланс клиента.
В чате `ADMIN_CHAT_ID` клиентской стороны нет: команда используется для клиента
без кошелька и после расчета меняет только кассу выбранного города.

### Работа Со Временем И Сделкой

- Доступ: **менеджер**.
- `/время HH:MM` — ответом на карточку заявки добавляет/заменяет время в карточке и синхронизирует расписание.
- Кнопка `Выдано` — проводит депозит/выдачу по клиентскому кошельку.
- Кнопка `Сделка завершена` — помечает сделку в чате заявок и убирает из расписания.
- Кнопка `Сделка отменена` — помечает отмену и убирает из расписания.

Пример:

```text
/время 10:30
```

### Google Sheets

- Кнопка `Занести в таблицу` в чате заявок записывает сделку в Google Sheets.
- Для заявок `accept_short` payload хранится в БД, поэтому после рестарта бот может восстановить данные по номеру таблицы.
- При отмене заявки, уже занесенной в таблицу, бот спросит, удалять ли строки из таблиц.
- RUB-регионы (`RUB`, `РУБМСК`, `РУБСПБ`, `РУБПЕР`, `РУБТЮМ`) приводятся к `RUB` при записи в таблицу.

### AML

- Доступ: **менеджер**.
- `/амл <TRON_USDT_адрес>` — поставить AML-проверку в очередь.

### Операционные Инструменты

- Доступ: **менеджер**. Для `/акт` также требуется чат заявок.
- `/акт` — показать текущее значение счетчика акта.
- `/акт <сумма|expr>` — установить фактическое значение счетчика; бот покажет
  предыдущее значение и расхождение.
- `/отпр` — ответом на сообщение с кошельком клиента начать контроль отправки
  USDT с настроенного кошелька компании на указанный адрес.
- `/отпр <сумма>` — начать контроль; сумма служит ориентиром, фактический перевод
  может отличаться.
- `/отпр тест [сумма]` — запустить тот же сценарий в тестовом режиме.
- `/xe <FROM> <TO> <AMOUNT[%]>` — пересчитать валюту через Converter API;
  поддерживаются выражения, проценты и суффикс `k`.

Примеры:

```text
/акт
/акт 100000+25000
/отпр 10000
/отпр тест 10000
/xe EUR USD 1000-0.3%
```

После запуска `/отпр` управление выполняется кнопками сообщения: ожидание можно
продлить или остановить. `/отпр` — отдельный учёт перевода, а не исполнение заявки
на продажу. После подтверждения MAIN-перевода Tronscan бот одной транзакцией БД
списывает фактически отправленный клиенту USDT или зачисляет полученный от клиента
USDT и только затем отправляет чек. Тестовый перевод также учитывается отдельно.
Без указанной суммы ожидание запускается даже при нулевом балансе; счёт может
стать отрицательным. Повторное подтверждение того же перевода не создаёт проводку.

### Ордера И Курсы

- Доступ: **менеджер**; `/курс` работает только в `RATE_ORDERS_CHAT_ID`,
  `/гарред` — только в админском чате.
- `/ордер <курс>` — создать ордер на курс.
- `/курс <комиссия>` — ответом на сообщение ордера активировать отслеживание
  с положительной или отрицательной комиссией.
- `/гар` — показать глубину asks.
- `/гарп` — показать глубину bids.
- `/гар-` — показать первый bid.
- `/гарред` — создать/обновлять live-сообщение стакана в админском чате.

Примеры:

```text
/ордер 91.5
/курс -0.5
/курс +0.3
/гар
/гарп
/гар-
/гарред
```

### BestChange

Доступ: **менеджер** и только чат `BEST_CHANGE_CHAT_ID`.

- `/бест <покупка|продажа> <тюм|члб> <qty_usdt> <курс биржи> <курс клиента>` —
  провести сделку текущей датой. Также принимаются глаголы `купить` и `продать`.
- `/бест история <ДД.ММ.ГГГГ> <покупка|продажа> <тюм|члб> <qty_usdt>
  <курс биржи> <курс клиента>` — провести историческую сделку. Будущая дата и
  новая запись в закрытый месяц запрещены.
- `/бест отчет [ММ.ГГГГ]` — месячная справка; без аргумента берется прошлый
  месяц. Вариант `/бест отчёт` также поддерживается.
- `/бест итог` — показать все пять текущих балансов BestChange.
- `/бест закрыть ММ.ГГГГ` — идемпотентно закрыть месяц.
- `/бест выплата <партнер|coindrop> ММ.ГГГГ <сумма> <ссылка>` — после закрытия
  записать отдельную выплату партнеру или CoinDrop. Допустимы `партнёр`,
  `partner` и `коиндроп`.
- `/бест сторно выплата <ID> <причина>` — сторнировать выплату.
- `/бест сторно закрытие ММ.ГГГГ <причина>` — сторнировать закрытие; сначала
  нужно сторнировать связанные выплаты.
- `/бест исправить <ID> <покупка|продажа> <тюм|члб> <qty_usdt>
  <курс биржи> <курс клиента> <причина>` — исправить ошибочную сделку с
  сохранением исходной записи и истории корректировки.
- `/кошелек` — показать все пять счетов BestChange, включая нулевые.
- `/дай` — показать только ненулевые счета BestChange.

Примеры:

```text
/бест продажа тюм 10000 86.33 87.22
/бест история 10.08.2026 покупка члб 5000 85.70 85.10
/бест итог
/бест отчет 08.2026
/бест закрыть 08.2026
/бест выплата партнер 08.2026 125000 payment-2026-08
/бест сторно выплата 42 ошибочная сумма
/бест сторно закрытие 08.2026 повторное закрытие
/бест исправить 801 продажа тюм 10000 86.33 87.22 опечатка менеджера
```

Первого числа в 09:00 по `Asia/Yekaterinburg` бот публикует предварительную
справку за прошлый месяц. Для исторической даты также принимается `ГГГГ-ММ-ДД`,
для месяца — `ГГГГ-ММ`.

### Клиенты, Группы, Менеджеры

- Доступ: **админ-чат**.
- `/клиенты` — список активных клиентов.
- `/клиенты <группа>` — список клиентов группы.
- `/rmclient <chat_id>` — мягко удалить клиента с подтверждением.
- `/группа <chat_id> <группа>` — назначить клиенту группу.
- `/mgr` — список менеджеров.
- `/mgr + <user_id> [имя]` — добавить менеджера.
- `/mgr - <user_id>` — удалить менеджера.

Примеры:

```text
/клиенты
/клиенты VIP
/rmclient 123456789
/группа 123456789 VIP
/mgr
/mgr + 123456789 Константин
/mgr - 123456789
```

### Отчеты И Балансы

- Доступ: **админ-чат**.
- `/бк` — все ненулевые балансы клиентов.
- `/бк <валюта>` — клиенты с балансом по валюте, фильтр `|баланс| >= 1`.
- `/бк <валюта> +` — клиенты с положительным балансом.
- `/бк <валюта> -` — клиенты с отрицательным балансом.
- Ежедневные отчеты отправляются в `SCHEDULE_CHAT_IDS`.

Примеры:

```text
/бк
/бк USDT
/бк RUB +
/бк USD -
```

### Рассылка

- Доступ: **админ-чат**.
- `/всем` — начать рассылку всем активным клиентам.
- `/всем <группа>` — рассылка клиентам указанной группы.

Сценарий:

1. В админском чате отправить `/всем` или `/всем VIP`.
2. Ответить на сообщение бота текстом, фото или альбомом.
3. Проверить preview.
4. Нажать `Отправить рассылку` или `Отменить рассылку`.

### Админская Ручная Заявка

- Доступ: **админ-чат**. Команда формирует и отправляет карточку, но сама не
  изменяет балансы.
- `/заявка <от_кого> <пд|пе|пт|пр> <сумма/expr> <од|ое|от|ор> <сумма/expr> [комментарий]`

Примеры:

```text
/заявка Клиент_Иванов пр 100000 от 100000/65 Приоритет
/заявка Петров /пт (700+300) /од 1000 срочно
```

### Офисы

- Доступ: **все**.
- `/екб` — карточка офиса Екатеринбург.
- `/члб` — карточка офиса Челябинск.
- `/тюм` — карточка офиса Тюмень.

### Калькулятор

- Доступ: **все**.
- `/calc <выражение>` — посчитать выражение.
- `/+100-5%` и похожие slash-выражения — быстрый расчет.
- Inline-калькулятор работает через `@bot <выражение>`.

Примеры:

```text
/calc (2+3)*100-50%
/1000-5%
```

## Архитектура

Фактический каталог PostgreSQL, владельцы данных и рекомендации по упрощению:
[`database_schema_audit.md`](database_schema_audit.md).

- `handlers/` — Telegram routing, auth, callback orchestration.
- `services/` — бизнес-сценарии и use-cases.
- `services/exchange/` — короткие обменные заявки.
- `services/cash_requests/` — наличные заявки, расписания, выдача, завершение/отмена.
- `services/wallets/` — кошельки: parser/query/mutation/undo/text/interaction.
- `services/broadcast/` — рассылки: service/session/preview.
- `services/rate_order/` — ордера и стаканы.
- `services/best_change/` — сделки BestChange, счета, закрытия и выплаты.
- `services/payment_watch/` — контроль исходящих USDT-переводов.
- `services/message_archive/` — архив сообщений, медиа, импорт и экспорт.
- `services/accounting/` — финансовые проводки и очередь исполнения.
- `services/aml/` — GetBlock AML.
- `db_asyncpg/repositories/` — специализированные репозитории.
- `db_asyncpg/repo.py` — совместимый фасад над репозиториями.
- `gutils/` — Google Sheets integration.
- `utils/` — общие утилиты и compatibility wrappers.
